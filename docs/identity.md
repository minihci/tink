# `tink identity groups`: the directory's people and groups

**Status: built and unit-tested; run live once, against a lab LLDAP (v0.6.3, 2026-10-13), for the table and headscale formats and for each failure listed below; the fragment was then checked and loaded in a throwaway Headscale 0.29.4.** It only reads. The design, with its reasoning and the experiments that were run, is in [identity-projector-design.md](identity-projector-design.md), and where it sits in tink in [what-tink-is.md](what-tink-is.md).

## What it does

```
tink identity groups --instance lldap --project id-lab --user reader --password-secret directory-reader
```
```
GROUP                            MEMBERS
admins                           alice
family                           alice, bob
lldap_admin (system)             admin
lldap_password_manager (system)  -
lldap_strict_readonly (system)   authelia
```

`--format json` prints the same as JSON. `--format headscale` projects the groups into the `groups` object of a Headscale policy:

```
tink identity groups ... --format headscale --group family --group admins [--headscale-instance headscale]
```
```
// generated by tink from the directory; do not edit by hand
"groups": {
  "group:admins": ["alice@"],
  "group:family": ["alice@", "bob@"],
},
```

## How it reaches the directory

It does **not** connect to the directory over the network. It runs a fixed script inside the LLDAP instance through the Incus exec API, so it works from anywhere that can reach the Incus server (`--remote` included) and needs no published port. The script logs in with a read-only directory user and runs one GraphQL query with `curl` and `jq`, which the upstream LLDAP image has. If either is missing, the error says so.

- **The credential is a tink secret** (`--password-secret NAME`, from `--secrets FILE`, default `secrets.yaml`). It travels on the script's standard input only: never on a command line, never in the instance's config. The user needs no administrator rights: a member of `lldap_strict_readonly` can read groups and cannot write **[lab]**.
- **It never writes** to the directory.

## The headscale format

- It prints a **fragment** for you to merge into the policy, never a whole policy. A Headscale policy with no `acls` or `grants` section is allow-all **[docs]**, so a fragment mistaken for a policy would open everything.
- **Deterministic:** groups sorted by name, members by id, one layout. The same directory gives the same bytes.
- **Which groups:** the `--group` names (repeatable), or, with none, every group except the directory's own system groups (`lldap_*`).
- **Member names:** `--member-format` (default `{id}@`, which is how Headscale's documentation writes a user). `{email}` is the other placeholder. Whether the default is right for users created through OIDC login is not yet known.
- **Findings** go to standard error. An **error** means no fragment is printed and the exit status is 1: a requested group that is not in the directory, a person with no id or no email where the format needs one, two people who would be written the same way, a group name the policy cannot use, a bad member format. A **warning** (a group with no members, nothing to emit) does not stop it.
- `--check` runs the checks and prints no fragment; the exit status is the answer.

## What Headscale does with the fragment

Tried against a throwaway Headscale 0.29.4 (the image production runs) **[lab]**:

- **A member with no Headscale user is accepted, silently.** `headscale policy check` calls the policy valid and a live reload completes; the member simply matches nobody. So a typo, or a person who has not got a Headscale user yet, is not caught by Headscale. **`--headscale-instance NAME` catches it:** tink runs `headscale users list -o json` inside that instance (through the exec API, no key needed: the command uses Headscale's local socket) and warns about each member that matches no user, by `<name>@` or by email. It is a warning, not an error, because Headscale does not mind and the user may be created later; the fragment is still printed. If the check cannot run (the instance is missing, or is not Headscale), that is an error and no fragment is printed. `--headscale-project`, `--headscale-bin` (default `/ko-app/headscale`) and `--headscale-config` (default `/etc/headscale.yaml`) say where Headscale is.
- **`headscale policy check -f FILE` is the gate:** it validates against the server's live users and rejects a real mistake (an unknown field) with exit 1. Run it before the policy goes live.
- **Getting the policy live.** tink can place the file with `kind: file`, but it neither validates it nor tells Headscale. In `database` mode, `headscale policy set -f FILE` run inside the container is validated, applies at once, needs no API key, and leaves the previous policy in force if the file is bad. In `file` mode a SIGHUP to the `headscale serve` process reloads it, and a bad file is only logged.
- Until the first `policy set` in database mode, Headscale is allow-all.

## A failed read is an error, never an empty list

An empty list rendered into a policy could lock everyone out, or, assembled with nothing else, allow everything. So each of these stops with a message that says which, and prints nothing: the instance is missing or stopped, `curl` or `jq` is absent, the login is refused (HTTP 401 with a wrong password), the query returns errors, the reply is not the JSON expected, the reply has no groups at all (LLDAP always has its three system groups), a group has no name, a member has no id.

## Not in this slice

Writing to the directory; pushing the fragment to Headscale or reloading it; a `kind: identity` resource and grants; the Authelia projector; pagination of a large directory (untested: the lab has a handful of users); more than one directory.
