# Design: reading groups from the directory and projecting them into the mesh policy

**Status: a design note, 2026-10-13. Nothing here is built.** It is the first slice of the identity role described in [what-tink-is.md](what-tink-is.md): the smallest piece that makes "tink reads groups from the directory" real. Claims are marked **[lab]** (seen on a real host), **[docs]**, **[code]** (this repository), **[proposed]** or **[verify]**.

## The job

The mesh control plane (Headscale) decides who may reach what with a policy file that names groups of people. The people and their groups already live in the directory (LLDAP). Today someone retypes them into the policy. This slice does two things:

1. **Read** the directory's groups and their members, through the engine's own interface.
2. **Project** them into the `groups` object of a Headscale policy, deterministically, so the result can be reviewed and merged by hand.

It writes nothing to the directory and pushes nothing to the control plane.

## Where the pieces sit

```
LLDAP (engine) --read--> identity.Snapshot --project--> Headscale "groups" block
   internal/identity/lldap     internal/identity     internal/mesh/headscale
```

- **`internal/identity`** is the role: a `Snapshot` (groups, each with members: id, email, display name) and a `Reader` interface. Nothing in it knows LLDAP.
- **`internal/identity/lldap`** is the engine: it fills a `Snapshot` from a running LLDAP instance.
- **`internal/mesh/headscale`** is a projector: a pure function from a `Snapshot` and a few options to the policy fragment, and a checker that returns findings. No network, no Incus.
- **`tink identity groups`** is the command that wires them. A new stack kind is not needed yet: that arrives with the first grant.

The same shape (a role package, an engine package, a pure projector) is what the second projector (Authelia's configuration) would follow.

## How the reader reaches the directory

**Default: through the Incus exec API on the directory's instance. [proposed]**

tink runs a fixed script inside the LLDAP container with `incusapi.ExecWithStdin`, which exists for "handing a command something that must not appear on a command line" **[code]**. The script logs in with a read-only user and runs one GraphQL query with `curl` and `jq`, and prints the JSON. The Go side parses it.

- **Reason.** On the lab host the directory is on a private bridge that the machine tink runs on cannot reach **[lab]**. Going through the instance API works from anywhere that can reach the Incus server, including under `--remote`, and needs no proxy device, no published port and no change to the network. It is the same reasoning as the ingress half of the helper, which reads and writes "through the ingress instance's file API" **[docs: helper.md]**.
- **What it requires.** `curl` and `jq` in the LLDAP image. The upstream image has both, with `bash` and `jo` **[lab]**. The reader checks for them and says so if they are missing.
- **Alternative.** A direct connection (LDAP or the HTTP API) from wherever tink runs, for sites where that is reachable. Cleaner code, and it needs a network path. The `Reader` interface leaves room for it.

## The credential

**A read-only directory user, kept as a tink secret, passed on standard input. [proposed]**

- In the lab, a member of `lldap_strict_readonly` could log in, read every group with its members, read every user with their groups, and was **refused** a write with `Unauthorized group creation` **[lab]**. So the reader needs no administrator.
- The password is a tink secret (`--password-secret NAME`), resolved by the existing secrets package and written to the script's stdin. It never appears on a command line, in the instance's config or in Incus's operation record. Output is passed through the existing redactor.
- Alternative: reuse the identity engine's bind user. It is in the right group already, but a dedicated reader keeps the two uses separable and revocable.

## The projection

**Input:** a `Snapshot`, the groups to emit, and how to write a member.
**Output:** the text of a `"groups"` object, in huJSON, to be pasted or merged into the control plane's policy:

```
// generated by tink from the directory; do not edit by hand
"groups": {
  "group:admins": ["alice@"],
  "group:family": ["alice@", "bob@"],
},
```

Rules:

1. **Deterministic.** Groups sorted by name, members sorted by id, one fixed layout. The same directory gives the same bytes, so a change in the policy is a change in the directory.
2. **Only the groups asked for.** `--group NAME` (repeatable). With none given, every group except the directory's own system groups (`lldap_*`). Reason: a policy should not enumerate everyone by default, and once grants exist the list comes from the grants. Alternative: all groups.
3. **Group names** become `group:<name>` as they are. A name the policy language does not accept is an error naming the group, not a silent rewrite.
4. **Member names.** Default: `<id>@`, which is how Headscale's own documentation writes a user (`alice@`) **[docs]**. Option: `--member-format '{email}'`. For users created through OIDC login the right form depends on how Headscale derives the name **[verify]**.
5. **Never a whole policy.** Headscale treats a policy file with no `acls` or `grants` section as **allow all** **[docs]**. A fragment that only had `groups` and was mistaken for a policy would open everything. So the output is clearly a fragment, and a later check (below) is the guard.

## Failure is an error, never an empty answer

If the instance is missing or stopped, `curl` or `jq` is absent, the login is refused, the GraphQL reply has errors, or the JSON is not the shape expected, the command fails with a message that says which. It never reports "no groups". The precedent in the helper is "a routes directory it cannot read is an error, never no routes" **[docs: helper.md]**: here an empty list rendered into a policy could lock everyone out, or, assembled with nothing else, allow everything.

## Findings (what `--check` reports)

| Finding | Severity |
|---|---|
| a requested group does not exist in the directory | error (non-zero exit) |
| a requested group has no members | warning |
| a member has no usable name for the chosen format (an empty email with `{email}`) | error |
| two members map to the same policy name | error |

Later, with grants: a grant that names a group the directory does not have is the same first finding, raised by `plan`.

## Tests

- **Unit, in CI:** the projector and the checker are pure, so table tests with golden output. The reader's parsing and failure paths run against a fake `ExecWithStdin` that returns canned output, including every failure listed above.
- **Fixture:** the GraphQL reply captured from the lab's seeded directory (groups `family`, `admins`, three users, the system groups).
- **Live, not in CI:** run against the lab LLDAP, with the read-only user, and compare with the fixture.

## Experiments the lab can answer before relying on this

1. **Does Headscale accept a group member that has no Headscale user?** If it rejects the policy, the projection has to be limited to people who exist there, or Headscale users have to be created from the directory first. **[verify]**
2. **Does `headscale policy check` accept the fragment inside a minimal policy?** A throwaway Headscale instance in the lab can run it without touching the real control plane.
3. **Does a SIGHUP sent from the host reload a file-mode policy?** The documentation says it does **[docs]**; the earlier attempt on the real control plane was not run. The throwaway instance can prove the delivery path.

## Not in this slice

A `kind: identity` resource and grants; the Authelia projector; writing to the directory (the declarative bootstrap path); pushing the policy to Headscale or reloading it; caching; pagination of a large directory **[verify]** (the lab has a handful of users); more than one directory.

## Open questions

1. The member-name format for OIDC-created Headscale users.
2. Whether a group with no members should still be emitted (an empty group in a policy is legal; it may hide a mistake).
3. The command's name: `tink identity groups` reads naturally now, and should survive the arrival of `kind: identity`.
